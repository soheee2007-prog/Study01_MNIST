# 웹 버전 / 데스크톱 버전 분리 설계

- 작성일: 2026-09-22
- 브랜치: `feature/web-desktop-split`
- 태스크 구성: 1 폴더 나누기 · 2 가중치 내보내기 · 3 정답 데이터 · 4 `모델.js` + 검증 페이지(모델) · 5 `전처리.js` + 검증 페이지(전처리·전체 경로) · 6 화면 파일 4개 · 7 배포와 문서

<details open>
<summary>a) 목표와 성공 기준</summary>

> 손글씨 숫자 인식 프로그램을 두 버전으로 나눕니다. 데스크톱 버전은 지금의 PyTorch + tkinter 프로그램을 **그대로 옮긴 것**이고, 웹 버전은 같은 가중치를 **외부 라이브러리 없는 순수 자바스크립트**로 추론해 GitHub Pages에 정적 파일로 올립니다. 두 버전은 같은 그림에 같은 답을 내야 합니다.

- 데스크톱: `desktop_version/`에서 `python train.py`, `python app.py`가 이전과 똑같이 동작
- 웹: 정적 서버로 열면 마우스·터치로 그려 인식하고, 결과, 확신도, 상위 3개 후보, 0~9 확률 막대를 표시
- 성공 기준 4가지(순전파 일치, 전체 정확도, 데스크톱 회귀, 웹 앱 동작)는 e 섹션의 표에 정리
- 배포: `main`에 push하면 GitHub Actions가 `web_version/`만 Pages에 배포
- 폴더마다 `CLAUDE.md`
- 하지 않는 것: 웹에서의 학습, 모델 구조 변경이나 재학습, npm·번들러·프레임워크

<summary>b) 폴더 구조 (태스크 1, 6)</summary>

> 기존 파일은 전부 `desktop_version/`으로 옮기고, `web_version/`은 새로 만듭니다. 웹에 필요한 가중치 파일과 검증 자료는 파이썬(PyTorch)이 있어야 만들 수 있으므로, 이를 만드는 스크립트는 `desktop_version/`에 둡니다. 결과물만 `web_version/`에 씁니다. 웹 폴더에는 브라우저가 읽는 파일만 남습니다.

```
(루트)
├─ CLAUDE.md  README.md          두 버전 안내로 다시 작성
├─ .gitignore                    기존 패턴(data/, __pycache__/)은 하위 폴더에도 적용됨 + web_version/검증데이터.json 추가
├─ .github/workflows/pages.yml
├─ docs/superpowers/             스펙과 구현 계획
├─ desktop_version/
│  ├─ CLAUDE.md                  새로 작성
│  ├─ README.md                  기존 README를 옮김
│  ├─ model.py  train.py  app.py  make_icon.py  icon.ico  mnist_cnn.pt
│  ├─ data/
│  ├─ 가중치내보내기.py          새로 작성 (태스크 2)
│  └─ 검증데이터만들기.py        새로 작성 (태스크 3)
└─ web_version/
   ├─ CLAUDE.md                  새로 작성 (태스크 7)
   ├─ index.html  스타일.css  그림판.js  앱.js     화면 파일 4개 (태스크 6)
   ├─ 모델.js                    (태스크 4)
   ├─ 전처리.js                  (태스크 5)
   ├─ 검증.html                  (태스크 4에서 만들고 태스크 5에서 검사 추가)
   ├─ 가중치.bin  가중치정보.json                   (태스크 2에서 생성, 커밋함)
   └─ 검증데이터.json                               (태스크 3에서 생성, 깃에 넣지 않음)
```

- 기존 파일은 `desktop_version/`으로 옮기고 `web_version/`을 새로 만듦
- `desktop_version/`에는 웹 버전용 파이썬 스크립트 2개(`가중치내보내기.py`, `검증데이터만들기.py`)가 추가됨
- `web_version/`에는 JS 파일 4개(`그림판.js`, `전처리.js`, `모델.js`, `앱.js`), `index.html`, `스타일.css`, `검증.html`, 가중치 파일 2개가 들어감. 정답 데이터 `검증데이터.json`은 로컬에서만 만들어 쓰고 깃에 넣지 않음
- 파일 이동은 `git mv`로 처리해 커밋 이력을 유지함(`git log --follow`로 추적 가능)
- 태스크 1이 폴더를 나누고, 태스크 6이 `web_version/`의 화면 파일 4개를 만듦

<summary>c) 데스크톱 버전의 코드는 수정하지 않음 (태스크 1)</summary>

> 이 저장소의 경로 규칙은 두 가지입니다. `app.py`의 아이콘 경로는 `__file__` 기준이라 `icon.ico`와 같은 폴더로 함께 옮기면 그대로 동작합니다. 반면 `가중치_파일`(`mnist_cnn.pt`)과 `./data`는 **현재 작업 폴더 기준** 상대 경로입니다. 따라서 옮긴 뒤에는 `desktop_version/` 안에서 실행해야 합니다. 이 점은 코드를 고치는 대신 `desktop_version/CLAUDE.md`와 README에 적습니다. 바탕 화면 바로가기는 저장소 밖에 있으므로, 대상 경로와 "시작 위치"만 `desktop_version\`으로 바꿉니다.

- 파이썬 파일 4개(`model.py`, `train.py`, `app.py`, `make_icon.py`)는 한 글자도 고치지 않고 옮기기만 함
- `icon.ico`는 `app.py`와 같은 폴더로 옮기므로 `__file__` 기준 경로가 그대로 성립함
- `train.py`와 `app.py`는 작업 폴더 기준 상대 경로(`mnist_cnn.pt`, `./data`)를 쓰므로 `desktop_version/` 안에서 실행해야 함(코드를 고치는 대신 CLAUDE.md에 적음)
- `data/`는 `.gitignore` 대상이라 `git mv` 대신 일반 이동으로 옮김(재다운로드 방지)
- 바탕 화면 바로가기(.lnk)의 대상과 시작 위치를 `desktop_version\`으로 수정
- 태스크 1은 이동 후 회귀 확인으로 끝남
  - `desktop_version/`에서 `python -c "import app; app.모델_불러오기()"`가 성공
  - 바로가기 속성이 새 경로를 가리킴
  - 바로가기를 더블클릭하면 앱이 열림

<summary>d) 가중치 내보내기 (태스크 2)</summary>

> `가중치내보내기.py`가 `mnist_cnn.pt`를 읽어 `web_version/`에 두 파일을 만듭니다. 이 모델은 합성곱 뒤마다 BatchNorm이 있습니다. 추론 때 BatchNorm은 고정된 선형 변환이라 **앞의 합성곱 가중치에 미리 합칠 수 있습니다**. 합쳐서 내보내면 자바스크립트는 합성곱·ReLU·최대풀링·완전연결만 구현하면 됩니다.
>
> - `가중치.bin`: 텐서 12개(합성곱 4개, 완전연결 2개의 weight/bias)를 float32 little-endian으로 이어 붙인 순수 데이터
> - `가중치정보.json`: 각 텐서의 이름, 형상, 파일 안 위치, 그리고 `model.py`에서 읽어 온 정규화 상수 `평균`, `표준편차`
>
> 형상과 상수를 자바스크립트에 하드코딩하지 않고 정보 파일에서 읽습니다. 지금 `0.1307/0.3081`은 `model.py` 한 곳에만 정의돼 있고 `train.py`와 `app.py`는 그것을 가져다 씁니다. 웹도 이 규칙을 지켜 값의 출처를 파이썬 하나로 유지하기 위해서입니다. 웹은 파이썬이 내보낸 값을 그대로 씁니다.

- ONNX 변환은 쓰지 않음. 브라우저에서 ONNX를 돌리려면 onnxruntime-web 같은 외부 라이브러리가 필요해서 "순수 JS" 조건에 어긋나기 때문
- 대신 `가중치내보내기.py`가 `mnist_cnn.pt`를 읽어 파일 2개를 만듦
- 실행은 `desktop_version/`에서 `python 가중치내보내기.py`로 함. 출력 위치는 스크립트 파일 기준 `../web_version/`
- BatchNorm 합치기: `배율 = γ / √(분산 + 1e-5)`, `W' = W·배율`, `b' = (b − 평균)·배율 + β`
- `가중치.bin`: 층 6개의 weight와 bias(텐서 12개)를 float32로 이어 붙인 숫자 데이터
  - 파라미터 467,818개, 1,871,272바이트(약 1.8MB)
  - 순서: 합성곱1~4 → 완전연결1 `[128, 3136]` → 완전연결2 `[10, 128]`
- `가중치정보.json`: 텐서별 `이름`, `형상`, `시작`, `개수`(float 개수 단위)와 정규화 상수 2개(0.1307, 0.3081)
- 정규화 상수를 자바스크립트에 직접 적지 않고 이 파일에서 읽음. 값의 출처를 파이썬(`model.py`) 하나로 유지하기 위함
- 스크립트는 저장 직전에 확인함: 합친 모델의 출력이 원래 모델(`eval()`)과 1e-4 이내로 같은지 PyTorch 안에서 비교하고, 다르면 저장하지 않고 종료

```json
{
  "형식": "float32-le",
  "평균": 0.1307,
  "표준편차": 0.3081,
  "텐서": [
    {"이름": "합성곱1.가중치", "형상": [32, 1, 3, 3], "시작": 0, "개수": 288},
    {"이름": "합성곱1.편향", "형상": [32], "시작": 288, "개수": 32}
  ]
}
```

위는 앞부분만 보인 예시입니다.

<summary>e) 정답 데이터와 성공 기준 (태스크 3, 검증은 태스크 4·5)</summary>

> 웹 코드가 맞는지 판단할 기준은 파이썬입니다. 검사 수단을 먼저 두고, 그 검사를 통과하도록 구현합니다(Superpowers의 test-driven-development 스킬). 그래서 태스크 3에서는 JS를 한 줄도 쓰기 전에 **정답 데이터**부터 만듭니다. 입력 그림은 MNIST 시험 이미지를 앱 그림판과 같은 280×280 흰 바탕·검은 글씨로 키운 것입니다. 이렇게 하면 웹 앱이 실제로 받는 입력과 같은 모양으로 전처리부터 추론까지 전체 경로를 검사할 수 있습니다.

- 정답 데이터(태스크 3): `검증데이터만들기.py`가 `web_version/검증데이터.json`을 만듦
  - MNIST 시험 이미지 앞 200장을 반전하고 NEAREST(최근접 이웃)로 10배 키운 280×280 그림(uint8, base64)
  - 파이썬 전처리 결과: `app.py`의 `전처리()`를 그대로 불러 쓴 784개 값
  - 예측 확률 10개: `model.py` + `mnist_cnn.pt`, `eval()`, softmax
  - 정답 라벨
  - (구현 계획에서 추가) `app.py`의 그리기 방식으로 PIL에 획을 그린 **그린 표본 30장**과 전처리 경계를 시험하는 **경계 표본 7개**. 10배 확대 그림은 bbox가 항상 10의 배수라, 어중간한 크기·짝수 반올림·부드러운 가장자리·캔버스 가장자리 닿음을 시험하지 못하기 때문. 이 표본은 성공 기준이 아니라 보조 검사(JS와 파이썬의 예측·전처리 일치)에 씀
  - 크기는 약 25MB(그림이 대부분)라서 **깃에 넣지 않음**: `.gitignore`에 `web_version/검증데이터.json`을 추가하고, 필요할 때 `desktop_version/`에서 `python 검증데이터만들기.py`로 다시 만듦
  - 저장소에 없으므로 GitHub Pages에도 올라가지 않음. 따라서 검증 페이지는 로컬 전용
- 검증 페이지(태스크 4, 5): `검증.html`이 같은 그림을 자바스크립트 경로로 통과시켜 파이썬 결과와 대조함
  - 외부 라이브러리 없는 작은 러너. 항목별 통과·실패와 실제 최대 오차를 표로 보여 줌
  - 끝나면 `document.title`을 `검증 통과 N/N` 또는 `검증 실패 K/N`으로 바꿔 브라우저 도구로 자동 확인할 수 있게 함
  - `검증데이터.json`이 없으면 "`python 검증데이터만들기.py`를 먼저 실행하세요"를 표시하고 실패로 처리함
  - 태스크 4에서 모델 검사를 넣어 만들고, 태스크 5에서 전처리 검사와 전체 경로 검사를 추가함
- 정답 데이터를 구현보다 먼저 만드는 이유: 검사 수단을 먼저 두고 그것을 통과하도록 구현하는 방식(Superpowers의 test-driven-development 스킬)
  - 태스크 4, 5는 검사를 먼저 추가하고 **실패하는 것을 확인한 뒤** 구현함
- 성공 기준

| 항목 | 기준 | 실측 |
|---|---|---|
| 순전파 일치 | 같은 28×28 입력(파이썬 전처리 결과)에 대한 확률의 최대 절대차 1e-4 이하 | 구현 후 기록 (태스크 4) |
| 전체 정확도 | 280×280 그림 → JS 전처리 → JS 모델 경로로 200장 중 97% 이상 정답 | 구현 후 기록 (태스크 5) |
| 데스크톱 회귀 | 터미널 실행(`desktop_version/`에서 `python app.py`)과 바탕 화면 바로가기(.lnk) 더블클릭 정상 | 구현 후 기록 (태스크 1) |
| 웹 앱 동작 | 그린 숫자를 인식하고 상위 3개 후보 표시 | 구현 후 기록 (태스크 6) |

- 보조 검사(성공 기준은 아니고, 실패 원인을 좁히기 위한 진단용으로 `검증.html`에 함께 표시)
  - 가중치 파일: 텐서 12개와 형상, `.bin` 1,871,272바이트 (태스크 4)
  - 전처리 단독: 280×280 그림 → JS `전처리.js` ↔ 파이썬 전처리 결과의 최대 절대차 (태스크 5)
  - 빈 그림: 흰색 280×280 → JS 전처리 결과가 `null` (태스크 5)

<summary>f) 순수 자바스크립트 추론 — 모델.js (태스크 4)</summary>

> 모델 구조는 `model.py`를 그대로 따르되, BatchNorm은 이미 합쳐졌고 Dropout은 추론에 쓰지 않으므로 뺍니다. 계산량은 약 1,900만 번의 곱셈·덧셈이라 순수 JS로도 수십 ms 안에 끝납니다. 따라서 WebGL이나 Web Worker 같은 최적화는 넣지 않습니다.

- 구조: 합성곱(1→32)·ReLU → 합성곱(32→32)·ReLU → 풀링 → 합성곱(32→64)·ReLU → 합성곱(64→64)·ReLU → 풀링 → 완전연결(3136→128)·ReLU → 완전연결(128→10)
- 공개 함수
  - `합성곱3x3(입력, 채널, 높이, 너비, 가중치, 편향, 출력채널)`: 패딩 1
  - `렐루(배열)`: 제자리 변환
  - `최대풀링2(입력, 채널, 높이, 너비)`
  - `완전연결(입력, 가중치, 편향, 출력수)`
  - `소프트맥스(logit)`
  - `async 모델_불러오기(경로 = ".")` → `{ 추론(입력784) → 확률(10), 평균, 표준편차 }`
- 모든 배열은 `Float32Array`, 메모리 배치는 PyTorch와 같은 채널 우선(C×H×W)
- 완전연결1 입력은 `64×7×7`을 C, H, W 순으로 펼친 것(`nn.Flatten`과 같음)

</details>

<summary>g) 전처리 — 전처리.js (태스크 5)</summary>

> 전처리가 다르면 같은 모델도 다른 답을 냅니다. 그래서 데스크톱 `전처리()`의 여섯 단계를 **순서와 반올림 방식까지** 똑같이 옮깁니다. 가장 까다로운 부분은 PIL의 `LANCZOS` 축소입니다. 브라우저 캔버스의 축소 방식은 브라우저마다 달라서 쓰지 않고, PIL 알고리즘을 JS로 직접 구현합니다.

- `전처리(회색조, 가로, 세로, 평균, 표준편차)` → `Float32Array(784)`, 빈 그림이면 `null`
- 단계
  1. 반전(`255 − 값`)
  2. bbox 찾기: PIL `getbbox`처럼 0이 아닌 픽셀 영역을 찾고, 오른쪽·아래 경계는 포함하지 않음
  3. 긴 쪽을 20으로 축소: 새 크기는 `max(1, round(길이·배율))`. `round`는 Python과 같은 짝수 반올림
  4. LANCZOS(a=3) 축소: 배율만큼 지지 폭을 넓혀 가로 → 세로 순으로 처리하고, 단계마다 0~255 정수로 반올림하고 범위를 잘라냄
  5. 28×28 바탕의 `((28−w)//2, (28−h)//2)` 위치에 붙이기
  6. 무게중심을 `round(14 − 중심)`만큼 정수 이동(범위 밖은 0)한 뒤, `(값/255 − 평균) / 표준편차`로 정규화
- 테스트용으로 `란초스_축소(값, 가로, 세로, 새가로, 새세로)`도 export
- 부동소수점 계산 차이로 픽셀 값이 ±1 정도(정규화 단위 1/255/0.3081 ≈ 0.013) 달라질 수 있음. 이 차이는 성공 기준이 아니라 보조 검사로 `검증.html`에 최대 절대차를 표시하고, 전체 정확도 기준(97% 이상)으로 판정함

<summary>h) 화면 — 그림판.js, 앱.js, index.html, 스타일.css (태스크 6)</summary>

> 화면은 데스크톱 앱과 같은 흐름입니다. 그리고 손을 떼면 바로 인식합니다. 여기에 휴대폰·태블릿 터치 입력과 좁은 화면 배치를 더합니다. 데스크톱 앱은 캔버스와 PIL에 같은 획을 두 번 그리지만, 웹은 캔버스 하나에만 그리고 그 픽셀을 읽어 인식합니다. 그래서 두 곳을 맞출 필요가 없습니다.

- `그림판.js`: `class 그림판 { constructor(캔버스, { 붓두께 = 20, 그리기끝 }) ; 회색조_가져오기() ; 지우기() }`
  - Pointer Events로 마우스·터치·펜을 한 번에 처리하고, `touch-action: none`으로 그리는 중 스크롤을 막음
  - 내부 해상도는 280×280으로 고정. CSS로 화면 폭에 맞게 줄이고 포인터 좌표를 환산함
- `앱.js`: 모델 로딩, 인식, 결과 숫자·확신도·상위 3개 후보(숫자와 확률)·확률 막대 10개 표시, 지우기 버튼, 오른쪽 클릭과 Delete 키로 지우기(데스크톱과 같음)
- `index.html`: 모듈 진입점 `<script type="module" src="앱.js">`
- `스타일.css`: 넓은 화면은 그림판과 결과를 좌우로, 600px 미만은 위아래로 배치하고 가로 스크롤이 생기지 않게 함
- 확인
  - 로컬 서버에서 실제로 그려 인식되는지 확인
  - 모바일 크기(375px)에서 배치 확인
  - 콘솔 오류가 없는지 확인

<summary>i) 배포와 문서 (태스크 7)</summary>

> GitHub Pages의 "브랜치에서 배포" 방식은 저장소 루트나 `/docs`만 게시할 수 있습니다. 그래서 GitHub Actions로 `web_version/` 폴더만 올립니다. 모든 경로가 상대 경로라서 `https://soheee2007-prog.github.io/Study01_MNIST/` 같은 하위 경로에서도 그대로 동작합니다.

- `.github/workflows/pages.yml`
  - `main` push와 수동 실행(`workflow_dispatch`)으로 동작
  - `configure-pages` → `upload-pages-artifact`(`path: web_version`) → `deploy-pages`
- 저장소 설정에서 Pages 소스를 "GitHub Actions"로 한 번 바꿔야 함(사용자가 직접)
- `CLAUDE.md` 3개
  - 루트: 두 버전의 관계, 모델이나 정규화를 바꾸면 `가중치내보내기.py`와 `검증데이터만들기.py`를 다시 실행해야 한다는 공통 계약
  - `desktop_version/`: 기존 내용, 실행 위치, 두 스크립트
  - `web_version/`: 모듈 구조, 외부 라이브러리 금지, 로컬 실행(`python -m http.server`)과 `검증.html`, 전처리 일치 주의, 배포
- README: 루트는 두 버전 소개, 웹 사용법, 배포 방법. `desktop_version/README.md`는 실행 위치를 반영해 갱신

<summary>j) 오류 처리</summary>

> 웹은 네트워크로 가중치를 받기 때문에 실패할 수 있습니다. 실패했을 때 아무 반응 없는 화면이 아니라 이유를 보여 줍니다.

- fetch 실패나 `.bin` 크기 불일치가 생기면 "모델을 불러오지 못했습니다"와 원인을 표시함
- 빈 캔버스는 인식하지 않음(`전처리`가 `null`을 돌려줌)
- `file://`로 열면 ES 모듈과 fetch가 막힘. 문서에 로컬 서버로 여는 방법을 적음
